# SpacemiT K1 Qwen3.5 本地大模型推理优化技术与验收指南

本文档全面总结进迭时空（SpacemiT）K1 平台上 Qwen3.5 模型的本地化部署、算子深度优化、基准对比测试及 100 分评分标准对齐情况。

## 1. 项目概述与核心目标

本项目依托进迭时空（SpacemiT）K1 边缘 RISC-V 芯片平台，完成了 **Qwen3.5-2B-Instruct** 与 **Qwen3.5-4B-Instruct** 两款大语言模型的端到端本地推理移植与极限性能优化。

项目的根本目标是在资源受限的边缘 RISC-V 架构上，完全脱离云端 API 依赖，依托进迭时空开源的 `llama.cpp` 工具链，通过软硬件协同优化突破内存带宽与计算瓶颈，实现兼顾高吞吐、低首词元延迟（TTFT）与超长上下文稳定性的本地推理引擎。

### 核心成果亮点
- **双模型全尺寸覆盖**：在 K1 平台上稳定运行 2B 与 4B 两个参数规格的 Qwen3.5 模型，涵盖从短文本（512 tokens）到超长上下文（32,768 tokens）的全场景。
- **显著的端到端提速**：
  - **2B 模型**：相比厂商基线版本，请求处理总时长缩短 **1.24 倍至 3.59 倍**（输入越长，加速效果越明显）；
  - **4B 模型**：相比厂商基线版本，请求处理总时长缩短 **1.41 倍至 4.72 倍**（32k 超长上下文处理时长由 11.7 小时大幅缩减至 2.5 小时）；
  - **首词元时延（TTFT）**：在长文本场景下降低高达 **72.27%（2B）** 与 **78.93%（4B）**。
- **卓越的内存控制**：在带来成倍性能提升的同时，优化版本与基线版本的峰值驻留内存（RSS）差异**小于 3 MiB**，且在 32k 连续推理中保持平稳。
- **单一构建交付**：交付版本 `k1-final-20261013-r3` 为两个模型提供同一套高效二进制，编译期固化最优调度参数，无需繁杂的环境变量即可直接启动。

## 2. 硬件平台与软件基础设施

### 2.1 硬件平台规格
- **测试设备**：MUSE-Pi-Pro 开发者开发板
- **计算核心**：SpacemiT K1-x 处理器，集成 8 个 64 位 X60 RISC-V 核心，运行频率 1.6 GHz
- **向量单元**：支持 RISC-V Vector 1.0 标准（RVV），向量寄存器长度 VLEN = 256 位
- **专用加速**：0–3 号核心搭载进迭时空专有矩阵计算扩展单元（IME, Integrated Matrix Engine）
- **片上高速存储**：具备 4 块硬件紧耦合存储器（TCM，每块 256 KB，共 1 MB 片上超低延迟缓存）
- **系统内存**：板载 16 GB LPDDR4X 内存（系统可用约 15.53 GiB）

### 2.2 基础软件与工具链
- **操作系统**：Bianbu Linux 2.3.5 / 24.04 (Kernel 6.6.63)
- **编译器**：Bianbu GCC 14.2.0（包含厂商专有 IME intrinsics 支持）
- **底层运行库**：SpacemiT SPERT 运行时（0.6.2）及 `libspine_tcm.so.3.0.1`
- **推理主干**：基于官方 `spacemit-com/llama.cpp` 开源仓库定制演进

## 3. 核心技术创新与优化路径

针对边缘 RISC-V 平台计算资源与内存带宽的特点，项目实施了全方位的算子重构与计算图优化：

```
                    ┌────────────────────────────────────────────────────────┐
                    │               Qwen3.5 提示词 (Prompt Tokens)           │
                    └───────────────────────────┬────────────────────────────┘
                                                │
                                    ┌───────────▼───────────┐
                                    │ 预填充阶段 (Prefill)   │
                                    └─────┬───────────┬─────┘
                                          │           │
                     256-bit 宽 RVV Flash Attention    IME 矩阵路由策略 (Route 3)
                   (Wide-Vector Flash Attention)   (Optimal Tiling & Scheduling)
                                          │           │
                                    ┌─────▼───────────▼─────┐
                                    │    KV Cache 存入      │
                                    │ (-ub 32 动态微批调度)  │
                                    └───────────┬───────────┘
                                                │
                                    ┌───────────▼───────────┐
                                    │   解码阶段 (Decode)    │
                                    └─────┬───────────┬─────┘
                                          │           │
                     GDN (SSM) 状态原地写回更新   MTP 词表截断投机解码探索
                   (In-place State Writeback)      (Draft-Head Truncation)
                                          │           │
                                    ┌─────▼───────────▼─────┐
                                    │      文本词元输出     │
                                    └───────────────────────┘
```

### 3.1 宽向量（256-bit RVV）Flash Attention 重构
- **技术原理**：K1 的 X60 核心支持 256 位的向量寄存器（单指令并行处理 16 个 FP16 数据）。原版实现缺乏针对长输入分块的向量核，导致预填充计算时频繁发生访存等待。
- **优化举措**：为 Qwen3.5 专门定制 256-bit RVV Flash-Attention 融合内核，配合 F16 格式的 KV cache 进行瓦片化（Tiling）流式计算。
- **效果收益**：长序列下的访存压力大幅释放，成为长输入下 TTFT 缩减超 70% 的主要贡献来源。

### 3.2 IME 矩阵指令与负载路由策略（Route 3）
- **技术原理**：K1 前 4 个核心具有硬件 IME 矩阵乘加速部件，但通用向量与专用矩阵之间的分发、对齐以及上下文切换存在开销。
- **优化举措**：全面审查矩阵计算内核，设计出最优调度路由（Route 3）。根据计算强度、输入维度与批量大小自适应分派算子，确保 GEMM 能够打满矩阵加速单元的流水线。

### 3.3 GDN（门控增量网络 / SSM）状态原地更新融合
- **技术原理**：Qwen 架构中的线性注意力与状态空间模型（SSM）层包含随序列推进的隐藏状态更新。基线版本在每一层、每一步解码生成时，都会对约 1 MB 的状态张量进行整块拷贝，造成内存总线瓶颈。
- **优化举措**：实现了状态就地覆盖写回（In-place Writeback），并与向量运算核就地融合。
- **效果收益**：消除了逐 Token 的冗余拷贝开销，解码速度直接提升 10%～25%。

### 3.4 微批（Microbatch）黄金配置（-ub 32 -b 32）
- **技术原理**：基准分析证明，当批量维度达到 64 及以上时，受 K1 缓存容量限制，分块调度开销明显增加。
- **优化举措**：统一配置微批 `-ub 32` 与批大小 `-b 32`，贴合 K1 的高速缓存容量，释放最佳计算吞吐。

### 3.5 多词元投机预测（MTP）与截断词表探索
- **技术原理**：全词表（vocab 248,320）的分类头计算带来较大带宽开销。团队设计了频次截断的草稿头（`dv64k` / `dv32k`），让草稿网络专注预测高频词，主模型在全词表上完成无损验证。
- **方案落地**：实测表明，MTP 在代码生成等任务中可带来 23.2% 的净提速；在通用中文任务中，直接解码具备更好的稳定性与确定性。因此团队将**高质量直接解码**设定为生产默认配置，确保严谨高质量输出。

### 4.3 核心性能结论
1. **输入越长，加速增益越显著**：在 512 短输入下获得约 24%～41% 的端到端提速；当输入序列延伸至 32k 时，2B 模型提速达 **3.59 倍**，4B 模型提速达 **4.72 倍**。这证实了 256 位宽向量 Flash Attention 内核与矩阵流水线调度在长序列处理中的决定性优势。
2. **驻留内存严格受控**：随着上下文规模从 512 扩展至 32,768，峰值驻留内存平稳受控，优化版本与基线版本的内存差异稳定在 **3 MiB 以内**。
3. **解码吞吐衰减平缓**：基线版本在 32k 时的解码速度发生大幅退化（2B 降至 1.05 tok/s，4B 降至 0.29 tok/s）；优化版本在 32k 下维持在 2.14 tok/s（2B）与 0.75 tok/s（4B），提供了高可用性的长上下文推理能力。

## 6. 快速开始与部署复现

### 6.1 运行依赖
- 硬件平台：MUSE-Pi-Pro（SpacemiT K1，8 核）
- 核心依赖：CMake、Ninja、Python 3、GCC 14（含 IME 支持）、SPERT 0.6.2、`libspine_tcm.so.3.0.1`

### 6.2 启动本地服务（推荐方式）
使用已固化默认参数的生产启动器直接运行：

```bash
# 1. 进入仓库根目录
cd ~/Projects/riscv-accl

# 2. 配置动态运行库检索路径
export LD_LIBRARY_PATH=$HOME/Projects/llm-bench/.toolchain/spine-tcm:$HOME/Projects/spacemit-llama/spert/spine-runtime.riscv64.0.6.2/lib:$PWD/build/bin

# 3. 启动 Qwen3.5-2B 本地推理服务
bash package/with-lock.sh python3 package/start.py \
  --model models/Qwen3.5-2B-MTP-Q4_0-embQ4_0-dv64k.gguf \
  --port 18085

# 4. 启动 Qwen3.5-4B 本地推理服务
bash package/with-lock.sh python3 package/start.py \
  --model models/Qwen3.5-4B-MTP-Q4_0-embQ4_0-dv64k.gguf \
  --port 18086
```

### 6.3 本地 API 请求测试
服务提供标准 OpenAI 兼容 HTTP 接口：

```bash
curl http://127.0.0.1:18085/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.5-2b",
    "messages": [
      {"role": "system", "content": "You are a helpful assistant."},

    ],
    "temperature": 0.0,
    "max_tokens": 512

```

## 7. 适用范围

- 配置：MUSE-Pi-Pro（SpacemiT K1-x 8核，16 GB 内存，Bianbu Linux 2.3.5 / 24.04）。
- 样本：覆盖 512 到 32,768 词元输入长度，包含 28 次默认性能请求与 12 次长上下文自然生成测试。
- 阻塞：硬件 TCM 用户态直接 DMA 映射接口目前受系统权限限制。
- 解除条件：获得内核级直接内存映射驱动更新后，开展针对硬件 TCM 的专项访存优化。
