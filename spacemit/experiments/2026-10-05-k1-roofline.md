## Method

- Audit the two deployed Qwen3.5 Q4_0 GGUF headers. Exclude the final MTP
  layer. Include the full tied output head once; input embeddings are row
  lookups, not another whole-table read.
- Compile an RVV full-buffer read kernel. Every source word contributes to
  a checked reduction, preventing dead-code elimination. Initialize and
  first-touch each worker's portion on its pinned core; exclude initialization
  and warm-up from the measurements.
- Buffers: 256, 1,024 and 2,304 MiB. Affinities: core 0, cores 0–1,
  cores 0–3, cores 4–7 and all eight. Five scans per case before and after
  inference. Count read bytes only, using decimal GB/s.
- Use the validated GEMM-routing library, with modes 0 and 3. Keep wide
  attention enabled, layout 0, four workers, batch/microbatch 32, F16 KV,
  no offloaded layers, no MTP and no context shifting.
- Two models × two prompt lengths (256/2,048) × two modes × three repeats:
  **24 cold requests**, each with exactly 64 output tokens and identical
  prompt tokens across matched arms. Alternate mode order. Restart the
  server for each request; exclude startup from server phase throughput.
- Collect separate optimized 2k/one-output-token CPU profiles. These are
  prefill diagnostics; sampled CPU shares are not removable wall time.
  A profiler failure is recorded without discarding valid timing measurements.
- Derive the reference from the median of all ten cores-0–3 scans at the
  predeclared working set: 1 GiB for 2B, 2.25 GiB for 4B. Do not pick the
  fastest affinity or launch after seeing results.

## Interpretation

Weight-only reference: bandwidth / main weight bytes per step. Also report
a one-pass F16 KV read estimate at the average decode context length.
Neither estimates actual DDR bytes: recurrent state, activations, repeated
loads, cache behavior and compute overhead remain. The streaming kernel
also has instruction overhead. A low inference/reference ratio does not
prove that its difference can be removed.

The datasheet's 32-bit 2,666 MT/s interface gives 10.664 GB/s raw peak;
the actual board memory clock is not established. No throughput-to-TOPS
conversion or claim of reaching the hardware limit is permitted.

This is a capped synthetic infrastructure benchmark, not answer-quality
validation. No production defaults are changed. Estimated runtime: 30–50
minutes; board execution budget four hours after the shared lock, lock
wait budget twelve hours. Both execution and verified collection use tmux.
