# K1 CPU 建模方法与现成模型对照

日期：2026-10-12。
状态：方法调查与历史数据对照已完成。
本轮没有新增板端测量。
通用 CPU 评估器仍未完成。

## 1. 结论

已有工作覆盖本项目需要的多项方法。
LLVM 和 GCC 已有 SpacemiT X60 指令调度描述。
本项目可以复用其参数分类和工具接口。
参数必须经过目标板核验。
现成调度描述不能直接提供新算法的预测置信度。

本轮把 LLVM 22.1.8 接入 676 个历史函数的对照清单。
482 个标量循环完成严格分析。
194 个向量或 IME 循环保留为本轮范围缺口。
全部候选均保留。

历史正收益对照包含第四轮和第五轮的 36 组重排。
LLVM 的方向一致为 12/36。
第六轮冻结模型的方向一致为 35/36。
第三轮冻结模型的方向一致为 36/36。
这些数据已公开，且各模型使用的训练数据不同。
这项对照不能证明任一模型对新算法的精度。

## 2. 可以复用的方法

| 工作 | 可以复用的部分 | 本项目必须保留的限制 |
| --- | --- | --- |
| [LLVM X60 调度源码](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.8/llvm/lib/Target/RISCV/RISCVSchedSpacemitX60.td)与 [llvm-mca 官方说明](https://llvm.org/docs/CommandGuide/llvm-mca.html) | 顺序发射、执行资源、操作数延迟和可自动重放的比较后端。 | 编译器调度描述不是完整 CPU。工具不模拟取指、译码和分支预测。 |
| [GCC X60 调度源码](https://github.com/gcc-mirror/gcc/blob/83b0befb611af61e0b4efbbc0ee235fe773ae891/gcc/config/riscv/spacemit-x60.md) | 用有限状态自动机描述跨周期资源预约。保留旁路与默认结果延迟的区别。 | 本轮只固定源码并核对语义。尚未执行 GCC 调度器的周期对照。 |
| [uops.info](https://arxiv.org/abs/1810.04610) | 按输入与输出操作数对测延迟。分开依赖链、独立吞吐和资源竞争。 | 复用实验方法。不能移用 Intel 参数。 |
| [uiCA](https://arxiv.org/abs/2107.14210) | 比较简单基线与详细模型。用实际基本块检查流水细节是否改变结论。 | 论文精度属于其 Intel 平台与测试集。不能移作 K1 精度。 |
| [OSACA](https://arxiv.org/abs/1910.00214) | 分开资源吞吐、关键路径和循环携带依赖。输出下界诊断。 | 其论文面向乱序架构。资源下界不能替代 K1 顺序发射周期。 |
| [gem5 Minor](https://www.gem5.org/documentation/general_docs/cpu_models/minor_cpu) | 显式流水级、队列、寄存器状态表、提交顺序和访存队列。提供逐周期状态轨迹。 | 默认配置没有经过 K1 标定。RVV 与 IME 的目标版本支持仍待核验。 |
| [ECM 模型](https://arxiv.org/abs/1509.03118) | 用基本微基准标定核内资源与存储层次成本。 | 论文平台为 Intel。K1 的层次传输与重叠关系必须另测。 |
| [DiffTune](https://arxiv.org/abs/2010.04017) | 从端到端实测拟合有效模拟参数。保留参数没有直接物理对应的可能性。 | 拟合参数不能证明模型结构正确。独立检查仍必须与训练分开。 |

上述方法共同支持分层建模。
本项目先建立可观测的执行状态，再标定存储层次。
真实算法验证用于检查组合后的预测能力。
本文的采用顺序是项目判断，不是这些论文对 K1 的实测结论。

## 3. 上游模型语义核对

LLVM 源码固定到 `llvmorg-22.1.8`。
文件 SHA-256 为 `1ac3cff0ed7a4f307641db47b7015e02a02d47c5904033fa75f454bd9751baff`。
该版本声明发射宽度为 2，微操作缓冲数量为 0。
该版本把 64 位乘法类的延迟设为 6。
源码说明普通 `mul` 与高位乘法采用该类的最坏延迟。
不能把此值直接解释为板端普通 `mul` 的已测延迟。

本项目早期固定的 LLVM 源码来自另一提交。
本轮没有混用两个版本的参数。
运行程序及其 LLVM 动态库另有散列收据。
上游标签身份与发行版运行程序身份分别记录。

GCC 源码固定到 `83b0befb611af61e0b4efbbc0ee235fe773ae891`。
文件 SHA-256 为 `ffe37f9d76afa9928ec3384acc7bfe7779213663c79ef16e6ea8cf488335277a`。
该文件的标量加载默认延迟为 5。
64 位整数乘法默认延迟为 5。
这些默认延迟与资源预约表达式具有不同含义。

GCC 的 `spacemit_x60_alu0,spacemit_x60_alu1` 表示相邻周期的资源预约。
逗号不表示两个可选执行端口。
竖线表示选择，加号表示同周期组合。
语法依据为 [GCC 官方流水描述说明](https://gcc.gnu.org/onlinedocs/gccint/Processor-pipeline-description.html)。
不能从资源名称数量直接推导硬件吞吐。

## 4. 对照工具与证据约束

新增工具为 `spacemit/bench/cpu-model/mca-baseline.py`。
工具从实际 ELF 提取已核验的固定循环。
汇编转写保留寄存器、加载偏移、计数减一和回边分支。
482 个转写循环重新汇编后，全部循环机器码与原 ELF 一致。
该检查包含循环控制指令。

服务器使用已有 LLVM 22.1.8 运行程序。
正式分析在 tmux 中全程持有项目共用锁。
运行程序 SHA-256 为 `4548cb6cc65b6368ac963c49a56588114caaf3cf67f8252e229b994affe879b9`。
LLVM 动态库 SHA-256 为 `4d136c3696669f8ab13afa868e29bc9f74f5a18bee9c938272dcc7e5de694eba`。

每个循环分别分析 128、256 和 512 次迭代。
周期估计采用 256 到 512 次之间的总周期增量斜率。
128 到 256 次的斜率作为收敛检查。
482 个循环的两个斜率差均为 0。
这项一致性不能证明硬件精度。
工具没有采用资源吞吐下界作为循环周期。

分析参数包含 `-skip-unsupported-instructions=none`。
工具必须核对静态指令数和总分析指令数。
工具必须保留错误输出与退出状态。
本轮 482 个范围内循环没有工具失败。
其余 194 个循环没有产生 LLVM 周期结论。

完整输出核对确认 156 对历史重排的数值一致。
其中 94 对属于本轮标量范围。
不同展开版本具有相关性，不能视作 94 个独立算法。
原始测量、冻结引擎与旧界限均未修改。
71 项工具检查通过。

首次准备过程误把 6 个单独控制函数视为配对。
该过程停止且没有启动原生测量。
修正后的输入为 `input-v2`。
失败记录与初次部分输出均保留。

## 6. 一个可检查的失败

第五轮 `r5-reorder-add-load-c4-p28` 具有相同的操作集合。
两个版本的完整输出一致。
K1 CPU 0 的实测周期约为 42.0010 和 29.9992。
实测比值约为 0.71425。
LLVM 预测周期为 32 和 86，比值为 2.6875。
第三轮与第六轮均预测为 42 和 29。

LLVM 顺序引擎检查全局的结果写回顺序。
较年轻指令预计先写回时，引擎可以推迟其发射。
相关实现见 [固定版本源码](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.8/llvm/lib/MCA/Stages/InOrderIssueStage.cpp)。
该规则为交错加载与整数操作的失准提供可检验解释。
本轮没有证明该规则是唯一原因。
本轮也没有证明 K1 具有某一种提交结构。

下一批实验必须区分结果完成、结果写回、架构提交与等待队列。
直接放大加载延迟无法独立区分这些机制。
第六轮长间隔读后写的收益误差继续保留。

## 7. 后续实施顺序

第一项是补齐标量机制的区分实验。
实验分别改变独立加载后的整数操作距离、目标寄存器复用和长依赖间隔。
相同目标寄存器与不同目标寄存器必须分开。
加载顺序与整数顺序必须互换。
只有改变地址依赖时才允许把结果归因于加载结果等待。
事件模型必须分别输出发射、操作数读取、完成和提交状态。

第二项是启动存储层次标定。
采用依赖指针链与独立访存流的配对工作集扫描。
分别改变工作集、步长、页覆盖、流数量和计算间隔。
按实测辨别缓存、地址转换、预取与访存重叠的有效行为。
不能继续用固定热地址加载代表实际算法访存。

第三项是冻结真实算法族后测。
数据必须同时包含改善、退步与接近不变的改动。
算法族必须与用于模型选择的代码分开。
输出包含收益误差、方向、排序价值与额外标定成本。
目标是指出哪些工作更值得投入。
本项目继续保留全部候选。

第四项是扩展 RVV、IME、前端与多核状态。
详细模拟后端在快速模型无法区分机制时提供状态检查。
采用 gem5 前必须先核验实际指令覆盖与数值输出。
本轮没有交付经过 K1 标定的 gem5。

