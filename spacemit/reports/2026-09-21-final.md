## 二、做了什么（按贡献排序）

### 1. TCM 链接修复（最大单点修复，3.8→5.2）

libspert 通过弱符号探测 `libspine_tcm.so`。该库不在 `LD_LIBRARY_PATH` 时，libspert **静默**使用 DDR 做 tile 缓冲，无任何日志。
实测带宽：真 TCM 写 24.7、读 9.26 GB/s；DDR 回退写 2.2、读 5.2 GB/s。修复带来 3.8→5.2 t/s。
探针脚本：`~/Projects/spacemit-llama/probe-tcm2.cpp`、`probe-devtcm.cpp`。

### 2. GDN 状态原地写回 + RVV 融合（commit f106a7d，从上游 rescue-1 移植）

18 层 SSM 每层每 token 省一次约 1 MB 状态拷贝，kernel 为 fused decode kernel。
上游 tg128 4.79→5.16；官方树 3.5→3.8。

### 3. MTP 投机解码全链路（commit 01949d8、0f2c9fb、6562c22）

- **2B**：unsloth 2B GGUF 自带 MTP（nextn）张量，requant 得到 `Qwen3.5-2B-MTP-Q4_0-embQ4_0.gguf`。
- **截断草稿词表头（dv64k）**：草稿 lm_head 是带宽大头（2B 286 MB、4B 365 MB 每草稿 token）。
  GGUF 手术追加 `nextn.shared_head_head.weight`，即 token_embd 前 65536 行（Q4_0）。graph_mtp 自动探测形状，把截断 logits 补 -inf 到全词表。该方法**构造性无损**：verify 永远用全词表。
  脚本：`gguf-add-dv32k.py`（参数化 N_ROWS/IL）。
- **4B MTP 从零手术**（`gguf-add-mtp-4b.py`）：unsloth 4B GGUF 不含 nextn。
  从 hf-mirror 拉 index.json，用 HTTP Range 精准提取 241 MB `mtp.*` bf16（共 15 个张量）。
  8 个权重转 q4_0，7 个 norm 转 f32（**+1，zero-centered RMSNorm**，见 conversion/qwen.py:303；漏掉则草稿全拒）。
  `block_count` 32→33，`nextn_predict_layers=1`。
- **n_max=3 最优**。2、4、5 均更差：草稿 launch 有固定开销，而 verify 的 M 增大。

### 4. 自适应投机门控 + checkpoint 回滚默认（多流逆袭关键）

发现链：启用 spec 后设 `cparams.n_rs_seq=3`（recurrent 回滚快照），每轮维护 SSM 快照拷贝（conc=8 时 dup_bytes 8.6%），且**屏蔽 GDN 原地快路**。多流即使不打草稿也亏 24%（9.85 对 13.49）。
解法：

- `SPINE_SPEC_MAX_ACTIVE`（默认 1）：活跃槽超过阈值自动停草稿，在途草稿正常验证。
- 默认 `n_rs_seq=0`（checkpoint 回滚，仅 SSM 状态），`SPINE_SPEC_RS=1` 切回快照模式。

结果：高并发追平或反超非投机（13.85），单路仅付 12%（5.40 对 6.31）。纯单路评测用 RS 模式。
**投机交叉点实测**：低并发（≤2）带宽受限，spec 赢；高并发（≥4）IME 算力受限，spec 亏。

### 5. pp ubatch 甜点（纯配置，pp128 +69%）

M≥64 的 BLOCK GEMM 调度效率骤降：pp128 在 ub=128 时仅 13.03，**ub=32 为 22.07**。
server 和 bench 一律用 `-ub 32 -b 32`。decode 和 verify 批量 ≤32，不受影响。

### 6. 已排除的死路（勿再试）

- 主权重低于 Q4_0 的量化：IME1 白名单仅 q4_0、q4_1、q4_K；实测 Q8_0 的 pp 慢 8 倍。
- IME2/q2_k 核：板上 `use_ime2: 0`，不可用。
- TCM tile staging 尺寸调整（A″）：中性；A′ 半相位锁步回退已证伪。
- spert 环境旋钮（HOT_SPIN、ARBITER、CTX_RVV、RT_PRIO）：全部无效果。
- checkpoint 数据通路优化：实测仅 16 ms/轮，损耗在 spert synchronize 流水线停顿（结构性）。
- 寄存器常驻 GDN 行变体：已拒绝。

## 六、2026-09-23 补充验证（4B）

以下在官方 fork 的 `port-gdn` 6562c22 上测得，均加载 spine-tcm。结果只适用于所列工作负载。

### 单路投机：使用 RS 快照回滚

`llama-server` 每组独立启动，参数为 4B-MTP-dv64k、`-t 4 -c 8192 --parallel 1 -b 32 -ub 32 -fa on --spec-type draft-mtp --spec-draft-n-max 3`。
同一 prompt（`The theory of relativity states`），`n_predict=128`，`temperature=0`，`seed=42`，`cache_prompt=false`。

| 回滚 / 草稿头 | 128 token decode（t/s） | 备注 |
|---|---:|---|
| 默认 checkpoint / dv64k | 2.704、2.712 | 两次独立启动 |
| `SPINE_SPEC_RS=1` / dv64k | **3.355、3.343** | 相同设置下比默认快约 24% |
| `SPINE_SPEC_RS=1` / dv32k | 3.203 | 比 dv64k 慢约 4%，不采用 |

三种配置输出的 SHA-256 均为 `cabf0208d3ac688bca04b885f73741a603d842c499179b212ca4663de90f3a89`。
dv32k 接受草稿 81/135，dv64k（RS）接受 84/126。更小草稿头节省的带宽不足以补偿接受率下降。
专用单路 4B 服务可在上述参数前设 `SPINE_SPEC_RS=1`。高并发仍用默认 checkpoint 加 gate 配置。
本文的 3.35 t/s 与第一节历史 3.20 t/s 服务配置并不相同，两者的提速百分比不可直接比较。

### 4B prefill 微批量

`llama-bench -p 128 -n 0 -t 4 -b 128 -fa 1`，模型为同一 4B Q4_0-embQ4_0。
初扫 `-ub 16/24/32/48/64`（各 1 次）为 8.99 / 9.08 / 9.13 / 9.25 / 7.28 t/s。
`-r 3` 复测后，`-ub 32` 为 9.149 ± 0.001，`-ub 48` 为 **9.268 ± 0.003 t/s**（约 +1.3%）。
`-b 128 -ub 48` 只用于 4B pp128 专项。综合 server 配置仍需单独测并发。
第一节与官方文档的 Q4_1 比较同时改变了量化和运行配置，应解读为端到端配置收益，而非单项代码收益。
