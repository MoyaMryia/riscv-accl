## 指令、调用栈及映射

原 core 的程序计数器为 `0x1c4612`，返回地址为 `0xa1244`。
当前匹配构建的指令为 `ld a4,168(a5)`。
原寄存器 `a5=0xc`，因此有效读取地址为 `0xb4`。
前一条指令为 `ld a5,8(a0)`，原寄存器 `a0=0x6a0028`。
该证据定位错误读取，不能定位错误参数的来源。

GDB 恢复九个原生栈帧。
栈内地址依次包含 `0x1c4612`、`0xa1244`、`0x1c4e60`、`0x1c5db2`、`0x19b7f2` 和 `Py_BytesMain`。
Python 可执行文件缺少内部静态函数调试符号。
板端也没有 `py-bt` 命令，不能恢复可靠的 Python 源级调用栈。
本次没有用邻近导出符号名替代未知静态函数名。

原 core 中父对象的类型指针对应 `PyFunction_Type`。
该类型的遍历函数地址为 `0xa120a`。
返回地址前的指令为 `ld a0,104(s1)`，随后调用回调。
父对象偏移 104 的原 core 字段值为 `0x6a8a28`。
故障参数却为 `0x6a0028`。
这一不一致仍待解释。

上游 [CPython 3.12.3 函数对象源码](https://github.com/python/cpython/blob/v3.12.3/Objects/funcobject.c)包含对应的字段遍历顺序。
[垃圾回收源码](https://github.com/python/cpython/blob/v3.12.3/Modules/gcmodule.c)包含检查对象类型后减少引用计数的回调。
据此推测故障位于函数对象的垃圾回收遍历路径。
这是源码与反汇编对应关系的推测，不是本发行版符号化的根因结论。
软件状态损坏、瞬态读取异常及未保存代码页的差异都未被排除。

原映射包含 Python、libc、libm、libexpat、zlib、动态加载器及 `_json` 扩展。
原映射没有 ggml、llama 或候选模型库。
该证据可以排除监控进程在自身地址空间直接执行这些候选库。
它不能排除跨进程共享系统资源的间接影响。

## 有限复现

两组均在 tmux 中全程持有原共用锁，不运行模型。
第一组按原标准输入方式执行 16 次，退出码全部为 0。
第二组在 GDB 下绑定 CPU 6 执行 16 次，地址随机化保持开启。
被调试进程全部正常退出，没有新 core。
GDB 随后的 core 保存命令因进程已退出而返回 1，不能据此判为 Python 失败。
230 个旧输入文件在复现前后的 SHA-256 核验通过。

复现读取的是已结束的旧结果目录。
它不能重建故障时变化中的摘要、最新日志或当时模型负载。
因此本次没有证明原场景可稳定通过。

补充诊断使用编码为 `74a8` 的同一 `c.ld a0,104(s1)` 指令。
CPU 0～7 依次运行，每次使用 16 MiB 数据和固定种子 42。
每个 CPU 执行 8388608 次读取，总计 67108864 次。
全部读取与预期值相同，八个退出码均为 0。
该有限模式不能排除其他访问模式、其他指令或罕见瞬态故障。
