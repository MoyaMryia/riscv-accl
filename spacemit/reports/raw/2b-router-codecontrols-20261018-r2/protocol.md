# 2B 两路路由端到端测试

## 固定方案

本次对照直接 HTTP 请求和自动路由请求，测量两个常驻后端下的完整请求时间。
直接解码和 64k 前缀 MTP 使用原 r3 二进制与同一份 2B 发布模型。
两路后端共用一个外层锁；各进程不重复取得锁。
生产入口、发布权重和原生代码保持不变。

| 项目 | 设置 |
| --- | --- |
| 题目 | 12 道新编请求，代码、中文、问答、长资料各 3 道 |
| 请求数 | 每题 baseline、routed 各一次，共 24 次 |
| baseline | 直接访问 direct 后端；两个后端均保持常驻 |
| routed | 访问自动路由代理，包含在线分类和转发 |
| 次序 | 按题目序号交替 baseline 优先和 routed 优先 |
| 线程、batch、ubatch | 4、32、32 |
| 上下文、slot、KV | 12288、1、F16 |
| 草稿长度、RS、lowacc | 3、0、0 |
| 分数保护 | 关闭；保持已固定模型和策略 |
| 缓存 | `cache_prompt=false`，每次核对实际复用数为 0 |
| 输出 | 首批上限 2048 token；重跑上限 4096 token，必须自然结束 |
| 请求时限 | 1800 s |
| 总批次预算 | 14400 s |

完整时间从客户端开始 HTTP 请求到读完 SSE 的 HTTP 响应边界。
计时包含分类、代理、预填充和解码。
服务加载、输入 token 核算、质量检查和证据文件写入在请求计时区间之外。
每次请求同时记录首次 token 时间（TTFT）、预填充时间、解码时间、输出长度、实际选路和分类耗时。

题目固定文件包含完整输入、人工参考事实和代码任务标识。
分类器训练、开发和分类测试文本不参与本次题目编写。
固定题目后全部执行，不按分类分数、草稿接受数或回答结果选择子集。

## 身份与运行检查

启动前核对原 r3、模型、SPERT、TCM 和本次脚本身份。
两个后端分别核对启动环境、实际配置、slot、上下文和 MTP 输出容量。
直接解码必须报告零草稿；MTP 必须报告非零草稿。
代理响应头给出本次实际路径，客户端用草稿计数检查路径绑定。
服务器报告的接受数保留原值，不用它推断首次草稿接受率。

客户端要求完整 `DONE` 事件，并继续读到 HTTP 响应边界。
结束原因、输入计数、缓存复用、slot 和输出上限检查沿用诊断工具。
进程崩溃、传输截断、超时或配置不符触发诊断停止。
减速、回答长度差异和代码功能错误不触发提前停止。

原生进程正常关闭必须返回 0。
原 r3 安装 SIGTERM 处理器；[完整头批次](../reports/raw/2b-full-head-ablation-20261017-r1/)的 12 次关闭均返回 0。
本次保留此门禁，不把原生进程的 `-SIGTERM` 作为成功关闭。
Python 代理使用默认 SIGTERM 行为，单独记录关闭返回值。

## 质量与结果计算

三个代码任务使用人工固定的数值、空输入、边界和输入不变性检查。
生成代码在独立受限进程内执行。
生成代码的功能失败写入质量结果；检查器内部故障使批次失败。
完整执行后，退出码 2 标记已记录的代码功能失败，采用判据单独报告。
非代码答案交独立审查者盲审，按原始输入评估事实、引用和指令遵循。
关键词出现与答案相同均不自动转成质量通过。

汇总同时给出总墙时变化和各类别的配对减速均值。
各类别平均减速必须不超过 3%。
整体平均质量分损失必须不超过 0.25，且不得新增事实、引用或代码错误。
质量审查完成前，`quality_gate` 和 `adoption_gate` 保持 `null`。
已知新增代码错误或速度门禁失败可以使对应门禁为 `false`。

资源记录包含仅加载 direct 的采样、两路常驻采样和逐请求前后采样。
记录每个进程的 VmHWM、RSS、PSS、私有页和机器可用内存。
PSS 是采样值；VmHWM 是进程高水位，两者分别报告。

## 首批配置故障与重跑

首批 `2b-router-e2e-20261018-054840-r1` 完成 18 次完整回答后，在首个长资料请求达到输出上限。
该回答输入 1972 token，输出 2048 token，完整请求时间 594.160 s，结束原因是 `length`。
批次返回 1；两个原生进程均正常关闭并返回 0。
原始回答、已完成结果和启动源码保持原样。
重跑在新目录将输出预算设为 4096 token，并重新执行全部 24 次回答。
题目、分类器、模型、原生配置和自然结束门禁保持不变。
重跑不把首批的 18 次回答混入新配对汇总。

## 代码手工对照

自动批次后，另起版本目录执行代码手工对照，保持原批次和模型不变。
固定选择原题集的全部 3 道代码题，不按分数、速度或质量筛选。
每题对照直接请求和经过代理的手工 prefix 请求，共 6 次回答。
手工请求设置 `X-Decode-Mode: prefix`，不执行分类。
两个后端均保持常驻，次序和完整时间定义与自动批次相同。
此步骤检查原生 MTP 候选和代理手工路径，分别报告速度与功能结果。

## 适用范围

配置：MUSE-Pi-Pro，原 r3，2B dv64k 权重，两个串行使用的常驻后端和一个独立代理。
样本：自动批次包含 12 个输入和 24 次完整回答，每类别有 3 个输入；手工对照复用其中 3 个输入，增加 6 次回答。
后续通用策略、多轮与并发任务由[路由原型适用范围](../serve/decode-router/README.md#适用范围)统一记录。
