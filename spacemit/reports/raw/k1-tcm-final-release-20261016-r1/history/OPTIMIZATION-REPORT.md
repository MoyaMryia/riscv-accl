# 优化报告 — Qwen3.5-2B @ SpacemiT X60 (MUSE-Pi-Pro)

日期：2026-09-11 · 基线 `llama.cpp` `df03399`，GCC 14.2，IME1

> **重要更正**：本报告前一版说"tg 是带宽墙（~5 GB/s）"——**那是错的**。
> 我当时用 `memcpy` 测带宽，而这块板子上 **glibc 的 `memcpy` 比硬件慢约 9 倍**
> （手写 49 GB/s vs glibc 5.8 GB/s）。真实 DRAM 带宽 **≈50–55 GB/s**。
> 结论因此完全不同：tg **不是**带宽受限。下面是重新定位后的结果。

---

## 0. 结论（TL;DR）

**瓶颈是 IME 矩阵单元在 M=1（单 token 解码）时的利用率，不是带宽、也不是汇编能解决的。**

- tg = 4.25 t/s，只用到 DRAM 的 **~8%**（`1.06GB × 4.25 / 50GB/s`）。
- 决定性证据：把"提示处理"的 batch 从 1 加到 16，吞吐从 **3.91 → 22.8 t/s（5.8x）**。
  而 **tg（4.25）≈ pp(batch=1)（3.91）** —— **生成就是"batch=1 的提示处理"**。
- 根因：IME1 有两个 kernel，`SQ4BitGemmM1Kernel`（GEMV）和 `SQ4BitGemmM4Kernel`（M=4，权重复用 4 次）
  （`ggml/src/ggml-cpu/spacemit/ime1_kernels.cpp:997`）。M=1 时矩阵阵列/权重复用被浪费掉 **~6x**。
- **汇编改不了这个**：阵列在 M=1 时就是空的，没有指令能填补空闲的硬件阵列。要填 M 只能靠**算法**。
  **更新：投机解码已实测——净亏损（§6）**：draft 模型自己也交 M=1 税；RVV/vendor/旋钮全部无增益（§7）。
  **TCM 暂存激活后 tg +9.5%（§8）**；其反相流水协议是跨核软件流水，剩余空间在搬运提速 + 相位重排（A′，§10.6）。吞吐杠杆仍是批处理。

## 1. 更正：内存带宽（之前测错了）

| 测试 | 1 线程 | 4 线程 |
|---|---:|---:|
| 流式读（4GB） | 16.6 GB/s | **55.1 GB/s** |
| 手写拷贝（4GB） | 23.9 GB/s | **49.4 GB/s** |
| **glibc `memcpy`（4GB）** | 5.3 GB/s | **5.8 GB/s** |

→ 真实 DRAM ≈50–55 GB/s；glibc 的 riscv64 `memcpy` 是个 9x 慢的坏实现（与本题无关，但说明
**任何用 `memcpy` 当带宽基准的结论都不可信**）。

tg 实际带宽 = 1.06 GB × 4.25 = **4.5 GB/s = DRAM 的 ~8%**。**没到带宽墙。**

## 2. 真正的瓶颈：GEMV vs GEMM（M 维度）

`llama-bench` 提示处理 batch 扫描（Q4_0-emb，t=4，ub=128）：

| n_prompt | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|---:|---:|
| t/s | **3.91** | 6.98 | 11.94 | 19.04 | **22.83** | 23.20 | 22.35 |

- n=1（纯 GEMV）**3.91 t/s**；n≥16（GEMM）**~23 t/s** → **5.8x**。
- **tg 4.25 ≈ pp(n=1) 3.91**：生成和"batch=1 的提示处理"是同一件事。
- 即：**每个 token 都单独做一次 GEMV**，而 IME 在 M=1 时效率只有 M≥16 的 ~1/6。

算力视角：pp(batch≥16) ≈ 82 GFLOP/s(int8)；tg ≈ **16 GFLOP/s** —— 同样的权重、同样的指令，
只因为 M=1 阵列利用率低。

## 3. "汇编能不能解决？" —— 逐条回答

| 候选 | 能解决吗 | 依据 |
|---|---|---|
| **tg 的 5.8x（M=1）** | **不能** | M=1 时矩阵阵列结构性空闲；没有指令序列能填补空闲阵列。必须给 M>1。 |
| 手写 M1 GEMV kernel | 有限、且难 | M1 kernel 只跑到 4.5 GB/s（11x 低于 DRAM）。**若**是延迟/流水问题，prefetch/软件流水**可能**帮上，但这是厂商已专门优化的 kernel，收益不确定、维护成本高。 |
| 通用 RVV 算子（softmax/rope/norm/glu） | 有，但很小 | ggml 的 RVV 映射硬编码 `GGML_F32_EPR=4`/LMUL=1，而本芯片 **VLEN=256**（f32m1 可装 8）→ 只用了一半向量宽度。但实测合成循环 **仅 1.14x**（这些算子本身是延迟/访存受限），且它们只占零头 → **整体 <2%**。 |
| 编译器 `-march` 扩展 | 否 | 试过，±1%（噪声）。 |

**结论：汇编不是这个问题的杠杆。** 唯一有理论空间的（M1 kernel 的流水）落在厂商 kernel 里，
性价比低、风险高。

## 4. 杠杆候选（算法，均不碰汇编）

1. **投机解码（speculative decoding）— 针对单用户延迟。** ❌ **已实测净亏损，见 §6。**
   一次前向验证 N 个 draft token → 该前向的 matmul 是 **M=N** → 直接吃到 GEMM 路径（快 ~6x），
   且**一份权重读产出 N 个 token**。这正是对着"M=1 浪费"打的——但 draft 模型自己解码也是 M=1 GEMV，
   也要交同一笔税。实测（Qwen3.5-0.8B draft，家族最小）：全深度 **1.0–2.3 t/s vs 基线 4.1**。
2. **批处理 / 多并发 — 针对多用户吞吐。** 实测（llama-server `-np`）：

   | 并发 | 聚合吞吐 |
   |---:|---:|
   | 1 | 3.91 t/s |
   | 2 | 6.00 t/s |
   | 4 | **7.70 t/s** |

   → 4 路并发聚合 **~2x**（单请求延迟从 3.91 降到 1.93）。并发越高越接近 GEMM 效率。
3. **KV cache 量化**：只对超长上下文有意义。

## 6. 投机解码实测（2026-09-11 晚）：净亏损

**TL;DR：draft 模型跑在同一批 IME 核上、解码同样只做 M=1 GEMV，杠杆 #1 在本模型+硬件组合上被证伪。**

配置：draft = **Qwen3.5-0.8B**（家族最小，2026-03-02 发布；同词表、同 hybrid 架构，`common/speculative.cpp`
的兼容性校验直接通过）。unsloth Q4_0（484M）→ 按 `make-fast-model.sh` 同流程 requant emb/output→Q4_0
（416M，权重 100% 走 IME）。

> **坑**：`--spec-type` **默认 `none`**——只传 `-md` 不报错也不生效（速度=基线），
> 必须显式 `--spec-type draft-simple`。这个 commit 的 llama-cli 也没有 `-no-cnv`，
> 非交互用 `-st` + `</dev/null`（否则生成完进交互循环刷屏）。

实测（llama-cli `-n 256` greedy、`-t 4 -ub 128 -fa on -c 8192 -st`、固定提示词）：

| 配置 | Generation t/s |
|---|---:|
| 基线（无投机） | **4.1** |
| draft-simple n_max=4 | 2.3 |
| draft-simple n_max=8 | 1.5 |
| draft-simple n_max=16 | 1.6 |
| draft-simple n_max=32 | 1.0 |
| ngram-simple / ngram-mod | 4.1（=基线：普通文本 n 接受率≈0，白挂） |
| 0.8B draft 单独 M=1 解码 | 7.8 |

算账（为什么必亏）：

- draft 每 token 成本 = 1/7.8 ≈ **0.128 s**；target verify（M=n 走 GEMM，§2 表）每 token
  ≈0.053 s（n=8）→ 每接受 1 个 token 最多省 0.244−0.053 ≈ **0.19 s**，但为它要先花 0.128 s 的 draft 时间。
- 盈亏平衡所需等效接受率（N_accept/n_draft）：n=4 需 **0.87**、n=8 需 **0.74**、n≥16 需 **0.70**；
  实测 0.8B→2B 每 token 接受率 α≈0.7，且深度越深复利误差把等效接受率越拉越低 → 永远在亏损侧。
- **即使 α=100%，天花板也只有 ~5.5 t/s（n=8）**：draft 成本已经吃掉 GEMM 红利的大半。
  根因同 §2——draft 解码是 M=1 GEMV，而 0.8B 只比 2B 快 **1.9x**（7.8 vs 4.1），差距远不够。

翻盘条件（供后续想法对照）：

1. **近乎免费的 draft**：MTP 头（已验证 2B GGUF 内无 MTP 张量，`draft-mtp` 不适用），
   或 ~0.1B 级同族模型（Qwen3.5 家族最小 0.8B，不存在）。
2. **接受率 ≥0.9 的场景**：代码 / 模板 / 复读类文本（此时 ngram 类才有意义）。
3. draft 不交 M=1 税的硬件/实现：如厂商支持 M>1 drafting，或 draft 与 target 流水并行到不同核。

复现：`./bench-spec.sh`（单测 `./bench-spec.sh draft-n8`）。产物 GGUF：
`models/Qwen3.5-0.8B-Q4_0{,-embQ4_0}.gguf`。

## 8. TCM 暂存激活：tg +9.5%（2026-09-12）

**TL;DR：后端为 M=1 GEMV 设计的 TCM 瓦片暂存在本板被静默禁用；补齐三环节后实测 +9.5%，稳定 ±0.00，成为新的推荐配置。**

背景：`ime.cpp` 的 GEMV 有完整 TCM 分支（A 行暂存 `ime.cpp:405` / B 列瓦片暂存 `ime.cpp:435`，线程成对生产者/消费者）——把 DRAM 延迟藏进 TCM 搬运。TCM 不可用时整个分支跳过，GEMV 裸读 DRAM。

激活链路（逐环节实测）：

| 环节 | 状态 |
|---|---|
| 内核驱动 | ✅ `CONFIG_SPACEMIT_TCM=y` 已编译已 probe（`d8000000.tcm`），节点 `/dev/tcm` |
| 用户态库 | ✅ `libspine_tcm.so.3.0.1`，取自官方 [spine-runtime 0.6.0 release](https://github.com/spacemit-com/spine-runtime) 的 `spacemit-tcm_3.0.1_riscv64.deb`；ABI 兼容（后端 dlsym 的即 `spine_tcm_runtime_*`）。已固化到 `.toolchain/spine-tcm/` |
| 设备权限 | ⚠️ `/dev/tcm` 出厂 0600 root-only；实测 `sudo -n` 可用（README "no usable sudo" 已过时），`chmod 666` 解锁，**重启还原** |

复现：`./tcm-bench.sh [模型]`。运行时加 `LD_LIBRARY_PATH=.toolchain/spine-tcm:$PWD/llama.cpp/build/bin`，后端自动检测（日志 `tcm is available, blk_size: 131072, blk_num: 4, is_fake_tcm: 0`，真硬件非模拟）。

实测（tg128, -t 4）：

| 模型 | 无 TCM | 有 TCM | 增量 |
|---|---:|---:|---:|
| Qwen3.5-2B-Q4_0-embQ4_0 | 4.23 | **4.63** | **+9.5%** |
| TinyLlama-1.1B Q4_0 | 8.43 | **8.95** | +6.2% |
| Qwen3.5-0.8B-Q4_0-embQ4_0 | ~7.8 | **8.40** | ~+7% |
| Qwen3.5-4B-Q4_0-embQ4_0 | 1.91 | **2.03** | +6.3% |

注：`/dev/tcm_sync_mem`（共享内存 barrier 后端）在这颗 6.6.63 内核未注册（`/proc/misc` 只有 `122 tcm`），需更新内核（spacemit-com/linux-k1x）。barrier 目前回退 heap，不影响 TCM 暂存的 +9.5%。

## 9. 硬件空置地图与每 token 216µs 分解（2026-09-12，TCM 激活态）

方法：`/proc/stat` 每核 15s 采样；perf 函数级剖析（cpu-clock 199Hz + root——**这颗 PMU 的硬件 cycles 事件采样不工作**，计数正常）；strace futex 计数（工具：linux-tools-6.6.63 + strace，已装）。线程满转（futex≈0），CPU 时间占比 = 墙钟占比。

硬件空置：

| 硬件 | 利用率 | 证据 |
|---|---|---|
| cpu0-3（AI 核） | 100% 忙 | /proc/stat 采样 100.0% |
| cpu4-7（普通核） | **≈0%** | 0.0/0.0/0.1/1.5%——一半 CPU 硅片闲置 |
| DRAM 带宽 | **~9%** | 4.62×1.06GB ≈ 4.9 GB/s（实测带宽 50-55） |
| TCM（4×128KB） | **~3.5%** | 瓦片 ~4.5KB/块 |
| IME 矩阵阵列 | **~17%** | M=1 vs M≥16 的 5.8x（§2） |

每 token 216µs（4 线程聚合）：

| 步骤 | 占比 |
|---|---:|
| IME1 GEMV 计算（`LOOP_INNER360`/`LOOP_K360`/RVV 段） | 40.3% |
| **内存搬运（`memcpy_main_loop39`，TCM 暂存拷贝）** | **36.8%**（CPU 时间占比，非墙钟占比——反相协议下大部分已与伙伴核计算重叠，见 §10.6 修正） |
| SSM 状态更新（`gated_delta_net`） | 5.9% |
| `dup_bytes` 张量复制 | 3.2% |
| `ggml_barrier` 自旋 | 3.2% |
| `vec_dot_f32` / `repack_q4_0_16_bl`(1%) / 其他 | ~5% |

剩余机会（按性价比）：

1. **搬运提速 + 流水重排**：首次迭代（§10.6）证明"拆 barrier"与"朴素块化"都不行——反相协议是跨核软件流水，搬运提速必须与相位重排一起做。
2. **cpu4-7 卸载非 IME 算子**（SSM 5.9% + dup 3.2% + vec_dot 1.3%），需调度改造。
3. **查 repack 稳态 1%**：`repack_q4_0_to_q4_0_16_bl` 疑似运行时重复 repack（本应加载时一次完成）。

## 10. 下一步代码改造方向（2026-09-12 候选清单）

> 仅列方向与依据，供选型；每条开工前仍需按流程写定计划。验证基线统一用 `./tcm-bench.sh`（±0.00 可复现）+ §9 的 perf 套件。

### 10.1 TCM 暂存双缓冲 —— 最大单项，直接打 36.8%

→ **第一次迭代已完成（两 draft 均证伪），计划与实验记录见 [`PLAN-tcm-dbuf.md`](PLAN-tcm-dbuf.md)，迭代结果与修正后的下一步见 §10.6。**
原始设想（拆 barrier + 私有双缓冲）被实测否定：pair barrier 是跨核软件流水（一核算‖一核搬，半相反相），
拆掉 -5.4%；块化暂存若不做相位重排则 -20%。修正后的方向 = **A′ 交错流水重排**（见 §10.6）。

- **依据**：§9 剖析显示 36.8% 的时间在 `memcpy_main_loop39`（DRAM→TCM 瓦片搬运），且与计算**串行**（拷→barrier→算逐瓦片交替，`ime.cpp:435` 分支，线程成对 producer/consumer）。TCM 每块 128KB、瓦片仅 ~4.5KB——容量够 28 层深流水。
- **改法**：把线程对的暂存协议改成两级缓冲：拷瓦片 N+1 的同时算瓦片 N，barrier 从每瓦片一次降到每缓冲翻转一次；可顺带加大单次暂存的 NB_COLS 摊薄拷贝次数。
- **预期**：完全隐藏搬运 → 理论上限 ~7 t/s（216µs→137µs）；现实按 1.15-1.3x 估。
- **风险**：动厂商 kernel 结构；TCM 块 handoff（mem_get/wait/release）语义要吃透；M≠1 路径不能被破坏。

### 10.2 cpu4-7 卸载非 IME 算子 —— 吃掉 10% 且硬件现成

- **依据**：§9：SSM 5.9% + dup 3.2% + vec_dot 1.3% ≈ **10.4% 跑在 AI 核上**，而 cpu4-7 实测 0% 完全空置（半个芯片闲置）。
- **改法**：调度层改造——非 IME 算子（gated_delta_net/dup/elementwise）分派到 4-7 核的线程池，0-3 核专职喂 IME。先做无代码实验探路：TCM 激活态下重测 `-t 5/6/8`（§7 的 -t8 崩溃结论是 TCM 之前测的，gated_delta_net 占比变了，结论需要重验）。
- **预期**：净 5-8%。
- **风险**：跨簇 cache/一致性、barrier 粒度变粗。

### 10.3 repack 稳态 1% 排查 —— 最便宜的一单

- **依据**：`repack_q4_0_to_q4_0_16_bl` 在稳态解码占 1%——repack 本应在加载时一次完成。
- **改法**：先用 perf annotate 确认是哪个算子在反复触发；多半是某个小张量绕过了 `get_optimal_repack_type` 的缓存。
- **预期**：~1%，顺手拿。

### 10.4 M1 kernel 内循环微架构 —— 天花板最高，最不确定

- **依据**：40.3% 在 GEMV 计算环（`LOOP_INNER360` 等）；§3 已知 RVV 算子只用半向量宽度（VLEN=256 可装 8 个 f32 只用 4）。TCM 暂存已部分隐藏 DRAM 延迟，但计算环本身的 load→IME 依赖链可能仍空转。
- **改法**：先测量后动手——`perf annotate LOOP_INNER360` 看流水线气泡位置，再决定 prefetch/软件流水是否值得写。§3 的结论（合成循环仅 1.14x）在 TCM 生效后需要重验。
- **预期**：不确定，0-1.2x；测量先行，改动兜底。

### 10.5 系统侧：带 `tcm_sync_mem` 的内核

- **依据**：共享内存 barrier 在 6.6.63 未注册（§8 注），barrier 回退 heap；线程曲线暴露的派发/同步开销是它的靶子。
- **改法**：非 llama.cpp 代码——升级到 spacemit-com/linux-k1x 新内核或新版 Bianbu，重测 §9 看自旋/派发占比变化。
- **预期**：未知；属系统升级，收益需实测。

### 10.6 第一次优化迭代记录与下一步计划（2026-09-12）

**迭代结果**（分支 `tcm-dbuf-a`，正确性均为 3-prompt greedy 逐 token 一致；master 保持 4.63 基线）：

| Draft | 改动 | tg128 | vs 4.63 | 判定 |
|---|---|---:|---:|---|
| ① f738079 | 拆 pair barrier | 4.38 | -5.4% | ❌ revert（af11e3e） |
| ② 8eede28 | 32 列块化暂存（保留协议） | 3.72 | -20% | ❌ 相位失衡，master 已恢复 |

**认知修正（§9 两处）**：

1. **pair barrier = 跨核软件流水，不是纯开销**。协议把配对两核相位反相：一个核算（IME 忙）
   时另一个核搬（DRAM 忙），每半相换角色。证据：t1 串行 2.58 × ~1.8 ≈ 4.63（流水增益吻合），
   拆 barrier 即 -5.4%。起草时"barrier 不保护共享数据故无功能"的判断是错的——它同步的是**相位**。
2. **36.8% 是 CPU 时间占比不是墙钟占比**：大部分搬运已藏在伙伴核的计算里。
   真正的墙钟浪费 = 搬运本身太慢（4.5KB 小瓦片 ~3.3 GB/s/core）+ barrier/相位开销，而非"没重叠"。

**下一步计划（三选一，按预期收益排序；A′ 推荐）**：

1. **A′ 交错流水重排**（~30 行，draft ② 骨架复用）：保留 36KB 块化搬运（拷贝效率 3.3→6+
   GB/s/core），两核相位按半相交错——HP(2k+1): even 计算 E_k ‖ odd 搬运 O_k；
   HP(2k+2): even 搬运 E_{k+1} ‖ odd 计算 O_k。墙钟 → 计算受限（~87µs/tile 等效），
   预期 +10-25%。风险：prologue/epilogue/无工作线程的边界条件（draft ② 的死锁防护已就位）。
2. **B 显式分工流水**：一核专职搬运、一核专职计算——A′ 的极限形式；若 A′ 实测仍有裸露相位则上 B。
3. **转向无耦合方向**：10.2 cpu4-7 卸载（~10.4%）/ 10.3 repack 排查（~1%）——不碰流水协议，可与 A′ 并行。

**验收标准不变**（PLAN 文档）：greedy 逐 token 一致 + tg128 ≥ 4.63×1.10 ±0.05 + TinyLlama 不回归 + pp 无 >2% 回退。

### 不再回头

投机解码（§6）、ngram、纯 RVV 路径（§7）——已证伪，除非上述全部兑现后接受率场景改变。

## 11. 一句话

> tg **不是带宽墙**（DRAM 只用了 9%），而是 **IME 在 M=1 时的阵列利用率墙**：生成 = batch=1 的提示处理，比 batch≥16 慢 **5.8x**。
> **汇编填不了空的矩阵阵列**；投机解码填不动（draft 同样交 M=1 税，§6）；RVV / vendor / 旋钮全部无增益（§7）。
> **TCM 暂存是厂商设计内、本板被静默禁用的路径——激活后 +9.5%（§8）**；其反相流水协议是跨核软件流水（§10.6 修正），
> 剩余空间在搬运提速 + 相位重排（A′，§10.6）。
> 目前唯一实测有效的吞吐杠杆是**批处理**（4 路并发 2x）。
