The measured speed improvement currently recommended for cold prefill is the opt-in RVV F16 attention kernel. Direct decoding remains the correctness-preserving choice for arbitrary long code because the observed MTP code output first differs at generated index 179 (2B) and 303 (4B). Draft-length, target-logit, and RS rollback diagnostics are queued to locate that divergence.

## Next measurement decisions

1. Finish the already-running 4B integrated 12k RVV off/on pair and strict output audit; report a single-pair result as such.
2. Diagnose the first long-code direct/MTP token divergence using the queued draft-length, target-logit, and rollback sweeps. Until resolved, use direct decode when exact output is required on varied long prompts.
3. Analyze the queued 4B long-output Q4_0 KV check and full/window/window/full 12k MTP comparison. Adopt windowing for speed only if the interleaved comparison confirms it; its measured RSS savings stand independently.
4. For the small M4 claims, collect enough paired repeats to estimate run-to-run variation and a confidence interval. Do not spend a long board campaign on every matrix cell before identifying a configuration worth deploying.
5. Extend context length from 12k to 16k, then 32k/64k only with a compatible larger context allocation and explicit time/RAM limits. Record TTFT, prefill/decode curves, resident-memory jitter, KV allocation, output completeness, and any failures. The current 16k KV numbers are allocation comparisons, not 16k-prompt benchmarks.

Actual GPU layer offload requires a compatible PowerVR backend or other supported device; the measured OpenCL attempt transferred zero layers. Full paged scheduling requires allocation/reclamation and mapped attention that avoids the measured gather-copy cost. Neither has a justified speed claim on this board yet.
