# K1 候选自动筛选框架可行性与首个原型

日期：2026-10-11，Asia/Singapore。

## 结论

可以用 QEMU 建立功能检查与指令分析框架。
本机已验证通用 RVV、K1 有符号 `vmadot` 编码和 Linux 来宾内执行。
本机已实现四线程卷积原型的自动批次。
这些结果不能证明 QEMU 能准确预测 K1 耗时。
K1 周期模型与自动板端校准尚未实现。

## 官方支持与本机环境

[进迭官方示例](https://github.com/spacemit-com/riscv-ime-extension-spec/blob/master/example/README.md)提供 IME QEMU 包及 `max,vlen=256` 用法。
本次下载包为 `jdsk-qemu-v10.0.2.tar.gz`。
包 SHA-256 为 `27c551eb9481da65dec610d8016af4b432aafdbba5c58402ed2f9343736a0374`。
该包仅解压到 `lab/k1-qemu-feasibility-20261011/`。
系统工具没有替换。
其用户态和系统态可执行文件均报告版本 10.0.2。

本机已有 QEMU 11.1.1。
其处理器与机器列表没有具名 K1 模型。
本次通用 `rv64` 配置执行同一 `vmadot` 探针收到 SIGILL。
官方进迭包执行同一探针成功。
这只验证本次编码与配置，不代表验证了全部 IME 指令。
官方包的 `max` 也不能视为严格限制到 K1 指令集合的配置。

本次编码 `0xe207382b` 来自已保存的板端 `vmadot v16,v14,v0` 反汇编。
探针检查 16 组有符号输入。
每组连续执行两次点积累加。
全部 16 个输出元素与独立整数参考计算相同。
插件记录 32 次矩阵指令，符合固定工作量。
插件对两输入与结果记录的访问字节数也符合预期。

仓库已有 Debian 内核与 Alpine 根文件系统。
本次从根文件系统生成新的独立 initramfs。
通用 QEMU 与进迭 QEMU 都在 `virt` 平台启动该 Linux。
来宾报告 `riscv64` 与 `6.12.94+deb13-riscv64`。
RVV 检查在两者中通过。
IME 检查在进迭系统态来宾中通过。

`virt` 是通用虚拟平台，不能据此称为完整 K1 SoC 模型。
现有镜像可以检查程序、线程、系统调用与启动集成。
本次没有验证 K1 板级设备、固件、GPU、TCM 或完整驱动行为。
这一区别与 [QEMU 的 virt 平台说明](https://www.qemu.org/docs/master/system/riscv/virt.html)一致。

## 已实现原型

入口见 [框架说明](../bench/qemu-screen/README.md)。
插件兼容本机 API 7 与进迭包 API 4。
它按精确函数范围统计每个虚拟处理器的动态数据。
记录项为总指令、向量指令、有符号矩阵点积、读写次数和读写字节数。
向量访存另外记录，避免把函数常量读取误算为数据阵列读取。
热点范围不包含被调用函数。

批次先核验源文件、编译器和二进制身份。
随后执行固定形状与固定循环数。
每个适配器必须执行完整正确性检查并生成完整转储。
批次比较两个臂的全部转储哈希。
插件还核验热点确有指定数量的工作线程。
发现差异会停止后续形状，并保留全部已生成记录。

本次故意改变一个输出元素。
批次准确产生 `rejected-numeric-difference`。
这项负向检查未修改原候选代码。
它不能记为候选算法失败。

## 指标自检

自检使用 1024 个 F32 元素与每臂 64 次固定调用。
两臂均先验证全部输出。
基线先复制阵列再计算，候选直接计算。
总指令分别为 155916 与 82122。
向量读取字节分别为 524288 与 262144。
向量写入字节分别为 524288 与 262144。

这些数值精确符合自检工作量。
总读取各比向量读取多 4 字节。
差额来自函数内的 F32 常量读取。
初版自检错误地把总读取与阵列读取直接比较，因此停止。
修订后分别检查向量访存与总访存。
原失败记录已保留。

## 实际卷积原型结果

以下数据来自 `Conv::step` 的一次固定工作量执行。
配置为 VLEN=256、四个工作线程、单序列和连续输入。
编译使用 GCC 16.1.0、`-O3` 和 `-ffp-contract=off`。
函数增加禁止内联属性，以固定统计范围。
控制先拼接历史与输入，候选直接访问分开的来源。
全部输入、权重、输出、状态与保护区检查通过。

| 通道数 | 词元数 | 总指令变化 | 向量读取字节变化 | 向量写入字节变化 | 判定 |
|---|---|---|---|---|---|
| 6144 | 8 | +16.902% | -14.667% | -57.895% | 待板端短测 |
| 6144 | 32 | +16.979% | -12.027% | -52.239% | 待板端短测 |
| 8192 | 8 | +16.950% | -14.667% | -57.895% | 待板端短测 |
| 8192 | 32 | +17.009% | -12.027% | -52.239% | 待板端短测 |

这是指令与访存之间的取舍。
总读取字节在 32 词元形状反而增加约 1.29%。
不能只报告向量读取减少而忽略其他读取。
全部四种形状均保留 `needs-board` 状态。
本次批次的执行与插件构建合计约 1.0 s，不含候选编译。
这是本机该短批次的处理时间，不能推广到模型测试。

## 自动化边界与后续结构

建议采用以下阶段。

```mermaid
flowchart LR
    A[冻结源码和验证计划] --> B[编译和指令能力检查]
    B --> C[完整数值和状态对照]
    C --> D[热点指令和访问指标]
    D --> E[K1 算子短测]
    E --> F[完整模型状态与冷请求门槛]
```

前四个阶段已有可运行原型。
当前只有卷积适配器接入通用批次。
B2 与 IME 调度仍只有上一批已准备的原型，尚未接入该批次接口。
K1 短测与完整模型阶段已有独立工具，尚未自动连接本框架。
新的板端任务必须等待当前组合任务释放共用锁。
框架没有自动启动额外板端任务。

数值错误与指令不支持可以尽早停止方案。
构建或加载错误必须归类为夹具故障。
单纯加载顺序变化可能完全不改变指令数。
这类方案不能因为指令数相同而被自动否决。
内存访问字节也不是 DDR 流量。
缓存命中、跨线程共享、预取及执行依赖都可能改变实际收益。

[QEMU 官方说明](https://www.qemu.org/docs/master/devel/tcg-icount.html)明确区分指令计数与周期准确模拟。
`-icount` 的虚拟时间不能用作 K1 性能结果。
[QEMU 插件文档](https://www.qemu.org/docs/master/about/emulation.html)提供指令、访存和简化缓存模型接口。
这些接口可作为后续框架基础，不等于已实现 K1 微架构模型。

[K1 数据手册](https://github.com/spacemit-com/docs-chip/blob/main/en/key_stone/k1/k1_docs/k1_ds.md)给出每核 32 KB 指令缓存和 32 KB 数据缓存。
手册还给出每簇 512 KB 二级缓存。
QEMU 示例缓存插件的二级缓存按核配置，不能直接替代 K1 的簇共享结构。
后续必须补充共享结构、替换策略、行大小、延迟和一致性假设。
缺失参数必须标为假设，并在板端校准。
没有校准的周期估算只能作为待验证排序。

## 故障保留与证据

初版计数自检的范围错误已保留。
第二版来宾计算通过，但新启动脚本使用错误的 `/bin/poweroff` 路径。
该脚本退出使来宾初始化进程结束，内核因此发生 panic。
修订为已有的 `/sbin/poweroff` 后，来宾检查通过并正常关机。
这些是本次框架夹具故障，与旧 Python 监控段错误无关。
旧 Python 段错误调查没有恢复。
