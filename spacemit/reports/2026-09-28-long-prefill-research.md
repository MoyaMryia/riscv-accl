# Faster long-context prefill on MUSE-Pi-Pro: GitHub and Google Scholar scan

> Dated campaign snapshot. Measurements apply to the stated workload and date.
> Queued/running statements below are historical; use the
> [current guide](../DOCS.md) and the [reports index](README.md) for later results and current status.

Date: 2026-09-28. Scope: the required Qwen3.5 2B/4B GGUFs on the SpaceMiT K1/X60 board and the official SpaceMiT llama.cpp fork. Papers were located through Google Scholar and checked against their primary manuscripts; implementations and failure reports were checked on GitHub. External speedups below are **not** measured gains on this board.

## The measured bottleneck

The completed [2B 32,768-token request](raw/2026-09-25-lifecycle/2B-q4w-f16kv-32768-rvv1-bounded.jsonl) used Q4_0 weights, F16 K/V, four threads, `-b 32 -ub 32`, and the opt-in 256-bit RVV attention path. Cold TTFT was **3,291.21 s (54 min 51 s)** at 9.96 prompt tokens/s. Peak RSS was 2,768.4 MiB with no swap or OOM. The [server log](raw/2026-09-25-lifecycle/2B-q4w-f16kv-32768-rvv1-bounded.log) shows each 32-token microbatch rising from **1.38 s near token 256** to **2.24 s near 8k**, **3.19 s near 16k**, and **5.11 s near 32k**. The roughly linear per-microbatch increase with processed context makes attention/history traffic the first profiling target, although these timings alone do not isolate the operator. The current tiled kernel uses 64 query and 64 KV cells per tile, while each server microbatch carries only 32 tokens. The model's [official config](https://huggingface.co/Qwen/Qwen3.5-2B/blob/main/config.json) has 256-dimensional full-attention heads and one full-attention layer in every four.

## Ranked paths

| Priority | Path | Relevance and constraint | First falsifiable test |
| --- | --- | --- | --- |
| 1 for repeated documents | Keep the exact prefix hot in the same server process | The [llama.cpp server documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) says `cache_prompt=true` evaluates only the unseen suffix. Our [local 2k test](2026-09-25-lifecycle.md) cut second-request TTFT from 110.87 to 0.45 s for 2B, with the same output hash. This is the only already measured order-of-magnitude latency reduction for repeated input. Hybrid recurrent checkpoints complicate reuse: upstream [Qwen3.5 reprocessing](https://github.com/ggml-org/llama.cpp/issues/20225) and [slot-save/restore](https://github.com/ggml-org/llama.cpp/issues/25913) issues show why 2k success cannot be assumed at 32k or across restarts. | Same-process, same-slot 8k then 16k cold/warm/warm requests with `cache_prompt=true`; record `cache_n`, prompt tokens actually evaluated, TTFT, and output token hashes. Test 32k only if shorter checks reuse correctly. Do not rely on disk slot restore until checkpoint state is verified. |
| 1 for a unique cold document | Send fewer relevant tokens | [LLMLingua-2](https://arxiv.org/abs/2403.12968) reports 2–5× prompt compression and 1.6–2.9× end-to-end latency improvement on its evaluated tasks, with [public code](https://github.com/microsoft/LLMLingua). For code and multilingual material, deletion can remove critical details; this changes the input and has no exact-token guarantee. Deterministic query-directed retrieval of source spans is the simpler first candidate; the original document can remain local. | On a held-out set of real user questions, compare full document versus exact-span retrieval at 4k/8k/16k target budgets. Measure recall of required facts, answer correctness, cited source spans, and full request time including retrieval. Try learned compression only if retrieval misses too much. |
| 2 for a unique full 32k prompt | Profile and retune the exact RVV attention kernel | [FlashAttention for Scalable Vector Architectures](https://arxiv.org/abs/2608.18656) evaluated RVV on a Banana Pi BPI-F3, also a [SpaceMiT K1 board](https://www.banana-pi.org/en/product-news/547.html). Loop reordering, head unrolling, and K/V reuse are relevant to our 256-bit, 256-head tiled path. Its largest reported gains use scalar baselines or simulated wider vectors; on real 256-bit hardware its prefill advantage was strongest at 64–128 tokens, and adapting its ideas to a newer tiled implementation produced about 5% in that paper. A direct large-context gain here is unproven. Another [RISC-V vector FlashAttention paper](https://arxiv.org/abs/2510.06834) explores blocking and a faster approximate exponential on gem5; its published acceleration must not be treated as a K1 result, and approximate softmax may alter output. | Profile the existing 8k/16k run by operator. In an isolated build, compare `-ub 32/48/64` at identical prompt/context/model settings, then a kernel-only query/KV tile and loop-order sweep if attention dominates. Check full output token IDs and server TTFT; revert any variant that helps the kernel but hurts end-to-end time. |
| 3, after profiling | Parallel/chunked Gated DeltaNet prefill | The [GDN inverse-approximation paper](https://arxiv.org/abs/2606.06034) reports up to 5× **kernel-level** speedup on Qwen3.5-family models, but targets NPU-style chunked linear attention, uses an approximation, and does not provide a drop-in K1/llama.cpp path. [FlashInfer's GDN prefill implementation](https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/gdn_prefill.py) requires CUDA. | Pursue only if operator profiling shows recurrent GDN work is a large fraction of 32k prefill and an RVV implementation can preserve required output quality. |

A [Tail-Replay paper](https://arxiv.org/abs/2608.30310), found via Google Scholar, is specifically relevant to **shared prefixes** in hybrid models: it reports 9.1× 32k TTFT speedup for Qwen3.5-4B on its serving setup with a 5% recurrent-state replay budget, while its LongBench average retained 98.9% and RULER 99.9% of full-prefill scores. It caches full-attention KV and hidden outputs, then **approximates** the recurrent state from a recent tail. It requires a new serving implementation, a previously computed prefix, and quality checks; it cannot accelerate a truly cold first request or guarantee bitwise identical output. Existing exact in-memory cache reuse should be validated first.

## What does not solve this 55-minute cold prefill

- MTP and n-gram speculation affect **decode**, not the first processing of 32k input; our long-code direct/MTP token mismatch remains open.
- Q8_0 weights were slower than Q4_0 on both tested model sizes in the [matched board comparison](raw/2026-09-25-lifecycle/lifecycle-weight-compare-2k.jsonl).
- Q4_0 K/V saved memory in the tested 4B run but cannot activate the current F16-only wide RVV prefill kernel; it is not a demonstrated 32k latency fix.
- The board's measured OpenCL path transferred zero layers, and the Vulkan route was dropped after its [driver audit](raw/2026-09-25-lifecycle/vulkaninfo-full.txt). GPU-only FlashInfer, CUDA, Triton, or ROCm speedups are not directly portable to this PowerVR/K1 setup.

**Decision:** For interactive use, first determine whether the 32k content is reused or unique. If reused, test same-process cache correctness at increasing lengths. If unique, benchmark real-task source retrieval to reduce the prompt. For a requirement to process every one of 32k tokens cold, profile the existing RVV attention path before implementing another kernel; no reviewed paper or GitHub patch establishes a guaranteed large speedup for this exact configuration.

## Same-process cache experiment (completed 2026-09-28)

The [gated board runner](../bench/run-prefix-cache-gated-board.sh) sent three identical requests per context to one 2B server process. Each context started a fresh server. The [gate](../bench/check-prefix-cache.py) required full 32-token output, identical token IDs and text, at least 90% cache reuse, and warm TTFT at most half of cold TTFT before advancing from 8k to 16k to 32k. Q4_0 weights, F16 K/V, four threads, batch and microbatch 32, and the 256-bit RVV path matched the long-prefill configuration.

| Prompt tokens | Cold TTFT | Warm TTFT #1 | Warm TTFT #2 | Cached prompt tokens on both warm runs | Result |
| ---: | ---: | ---: | ---: | ---: | --- |
| 8,192 | 450.54 s | 0.86 s | 0.95 s | 8,188 | PASS |
| 16,384 | 1,140.11 s | 1.52 s | 1.58 s | 16,380 | PASS |
| 32,768 | 3,302.07 s | 2.93 s | 2.83 s | 32,764 | PASS |

The server evaluated four prompt tokens on each warm request. All three requests at each length produced the same 32 token IDs and text. The raw [8k](raw/2026-09-25-lifecycle/2B-prefix-cache-8192-rvv1.jsonl), [16k](raw/2026-09-25-lifecycle/2B-prefix-cache-16384-rvv1.jsonl), and [32k](raw/2026-09-25-lifecycle/2B-prefix-cache-32768-rvv1.jsonl) records and the [driver log](raw/2026-09-25-lifecycle/prefix-cache-gated-driver.log) are archived.

**Practical decision:** Keep a 2B server process and its prompt cache alive when users revisit an identical long prefix. This removes almost all repeat-prefill delay, including at 32k. The first request still takes about 55 minutes, and this experiment does not establish reuse after restarting the server, changing the prefix, switching slots, or using 4B. Those are separate tests. For a unique full 32k input, source retrieval or cold-prefill profiling remains the relevant next optimization.

## Follow-up: changed question on a cached document

The [2026-09-29 changed-question test](2026-09-29-shared-document-cache.md) found a correctness limit that the identical-prompt experiment did not exercise. The 2B/8k and 4B/8k–16k warm requests reproduced their forced-cold answers with large TTFT reductions, but 2B/16k first differed at generated token index 5 despite caching 16,373 document tokens. The gate therefore skipped 2B/32k. Exact repeated-prompt success at 32k should not be generalized to arbitrary follow-up questions.
